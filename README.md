## Project overview
HASMA (Health & Wellness App) is a **planning-level initiative** aimed at designing and delivering a cross-platform mobile application to support well-being, healthy habits, and access to healthcare services.  

This repository documents the **Work Breakdown Structure (WBS)**, baseline project schedule, and supporting planning artifacts. It serves as the foundation for future development and guides both academic review and eventual handover to technical teams.

### Goals
- Produce a clear, actionable WBS linked to deliverables and owners  
- Prepare a baseline schedule, budget, and risk register  
- Document initiation, planning, execution, and closing phases  

### Audience
- Project managers and planners  
- Stakeholders & sponsors  
- Designers and technical leads reviewing scope & schedule  
- Academic reviewers assessing project methodology and planning artifacts

## How the WBS is organised
The WBS uses a **hierarchical decomposition approach**, where tasks are grouped into logical, manageable packages. Example top-level divisions:

1. **Initiation**  
   - Project charter  
   - Project proposal  
   - Stakeholder register  

2. **Planning**  
   - Requirements gathering  
   - WBS & schedule creation  
   - Risk analysis  

3. **Execution & Design**  
   - UX research  
   - Application & UI design  
   - Core feature development  
   - EMS/API integrations  

4. **Testing & QA**  
   - Test planning  
   - Functional, usability, and performance testing  
   - Security and compliance testing  

5. **Deployment & Closure**  
   - Release & deployment plan  
   - Maintenance handover  
   - Post-implementation review  

Each task includes:
- Deliverable name  
- Description / acceptance criteria  
- Owner / responsible party  
- Estimated duration  
- Dependencies (if known)

## Opening & editing project files (tips)
**Preferred tools**  
- [LibreOffice](https://www.libreoffice.org/) (Writer/Calc/Draw) — preserves formatting and structure.  
- PDF readers (Adobe Reader, Evince, Preview) — for viewing read-only exports.  

**Tips**  
- Keep a copy of the original file before editing. Use versioned filenames (see below).  
- Export to PDF before sharing for consistent formatting.  
- For diagrams, maintain vector source files (`.odg` / `.svg`) in `/assets/` for clean edits.  

---

## Versioning & file naming conventions
Use this format:  


Examples:  
- `project-wbs-v1.0_tokoloho-20250901.odt`  
- `gantt-baseline-v1.0_wambo-20250904.pdf`  

Rules:  
- Increment version for major changes (v1.0 → v1.1 for minor; v2.0 for major).  
- Include editor short handle + ISO date.  
- Preserve previous versions (do not overwrite).
